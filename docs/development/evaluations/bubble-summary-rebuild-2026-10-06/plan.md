# 圧縮プロンプト再構築の検証計画

2026-10-06。ユーザーが予算をリセットし、新たな上限$10を承認。過去の台帳は保存し、新しい実験キーだけに記録する。人工入力をアプリ共通API経路でOpenRouter Opus4.6へ送る。

1. 旧結果を全件再評価し、明示制約・意味や状態・暗黙文体・許容差・判定保留を分ける。既知の候補名を見た担当によるため盲検とはしない。
2. 原文＋プロンプト2種×置換文2種を同条件で比較。各3圧縮、同じ圧縮を複数質問と2種の置換文で使う。6/6応答を独立した6入力とは数えない。
3. 改善と失敗の両方からcompact用規則を整理。共通規則と単独/連続、一回生成、role/content入力を保持。候補を変える際は新フェーズで旧結果を上書きしない。
4. 原文・現行・再構築候補で開発ケースと未使用ケースを比較。圧縮の反復と後続生成の反復を区別。強制置換による診断と、本番の削減判定による原文維持を分けて記録する。
5. 既存36件を使って要約意味の回帰を確認。改善を示す領域と劣化・不確実な領域を併記。重要な違反を形式の改善と相殺せず、一度の違反だけで候補全体失格にもせず、少数回で差を確定しない。
6. API usage、プロバイダ、設定、入力、出力、応答ID、判定理由、費用を保存。関連テスト・型チェック・ビルド・差分確認後、既存の許可に従ってPR・main反映。

予算は保守的に予約し上限前に停止する。API失敗や中断の費用が不明なら予約を残す。原文維持は圧縮品質の改善と数えない。温度/モデルは別条件として扱い、結果を合算しない。
