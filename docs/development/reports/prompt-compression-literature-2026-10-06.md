# バブル圧縮の先行研究と検証方針

2026年10月6日。対象は、OpenRouter経由の生成モデルに渡せる編集可能なテキストへの圧縮。後続の質問が未定の会話履歴を対象に、意味、指示、文体、ニュアンスを維持することが要件である。

研究上の高い圧縮率を、そのままこの用途の目標値にはできない。質問に合わせて情報を捨てる方式、モデル内部の表現に圧縮する方式、一般用途のテキスト圧縮を区別する必要がある。今回確認した文献は、日本語の混合会話をOpus 4.6で処理し、任意の後続応答の文体まで保持する保証を与えていない。

## 方式と適用条件

| 研究 | 方式と報告された条件 | このアプリでの判断 |
| --- | --- | --- |
| [LLMLingua, EMNLP 2023](https://aclanthology.org/2023.emnlp-main.825/) | 小型モデルの評価を使ってトークンを削除する。GSM8Kでは20倍圧縮で正解率が約1.52ポイント低下。一方BBHでは7倍で約13.2ポイント低下した。§5.2、Table 1。 | テキスト出力はAPIに渡せる。ただし別の圧縮モデルが必要。「20倍」は会話全般の無損失圧縮を意味しない。 |
| [LLMLingua-2, ACL Findings 2024](https://aclanthology.org/2024.findings-acl.57/) | GPT-4から蒸留した保持・削除判定を学習。原語順を保つ抽出方式。LongBenchの約5倍圧縮では平均スコア39.1、原文44.0。§3–5、Tables 2、6。 | 次の質問に依存しない比較方式として有力。ただし学習済み分類モデルと実行環境が必要。論文の蒸留用プロンプトだけをOpusに移しても同じ方式にはならない。 |
| [LongLLMLingua, ACL 2024](https://aclanthology.org/2024.acl-long.91/) | 質問に応じた圧縮、文書の並べ替え、動的な配分。論文のLimitationは質問が変わると再圧縮が必要で、複雑・微妙な関係が課題とする。 | 将来の質問が未定の保存用バブル圧縮には直接適合しない。送信時の質問別圧縮は別機能・別費用になる。 |
| [RECOMP, Xu et al.](https://arxiv.org/abs/2310.04408) | 検索文書を質問に必要な文・要約へ圧縮する学習方式。不要なら空文字列にできる。論文導入の6%という結果はoracle条件を含む。 | 質問に答える証拠の選択には適する。会話履歴の未解決事項や将来有効な制約を捨てる判断の根拠にはできない。 |
| [Gisting, NeurIPS 2023](https://arxiv.org/abs/2304.08467) | 学習したモデル内部のgist表現。LLaMA/FLAN-T5で最大26倍圧縮を報告。 | 通常の編集可能な短文ではない。モデルの学習・内部アクセスが必要で、現行OpenRouterのテキスト経路にそのまま導入できない。 |
| [ICAE, ICLR 2024](https://proceedings.iclr.cc/paper_files/paper/2024/hash/0b276510ec2d3f6613a8b60c41ff0438-Abstract-Conference.html) | 学習したメモリ表現に圧縮し、対応するLLMで利用する。Llamaで4倍を報告。 | Gisting同様、表示・編集する圧縮文の代替にはならない。 |

抽出方式は原文にない語を作りにくいが、削除した語の意味までは保証しない。例えば「採用しない」から否定を削れば、残った語がすべて原文由来でも要求は逆転する。これはこのアプリの要件から導く判断である。

LLMLingua-2の§3.1は、文章の情報密度によって適切な圧縮率が変わると指摘する。公式実装には保持する語を指定する `force_tokens` があるが、これを指定すれば指示・文体全体を保てるという意味ではない。[論文](https://aclanthology.org/2024.findings-acl.57.pdf)、[公式実装](https://github.com/microsoft/LLMLingua)。

## 削減率と品質を分けて評価する理由

[Fundamental Limits of Prompt Compression, NeurIPS 2024](https://papers.nips.cc/paper_files/paper/2024/hash/ac8fbba029dadca99d6b8c3f913d3ed6-Abstract-Conference.html) は、圧縮量と回答の変化の関係を、対象モデルと質問の分布を含めて定式化する。これは一般的な日本語会話の安全な削減率を計算してくれる定理ではない。このアプリでは、同じ圧縮文を異なる次の質問とモデルで使う条件を評価に含める、という設計上の示唆として使う。

[Does Context Compression Preserve Refusal Alignment?, Canadian AI 2026](https://proceedings.mlr.press/v318/nguyen26a.html) は、内部表現への圧縮で、復元品質が高くても拒否動作が変化する結果を報告する。テキスト圧縮や文体の直接検証ではないが、復元・意味類似度だけでは後続動作を保証しないことを示す。こちらの提案は、文体・制約も後続応答で直接調べることである。

[Lost in Compression, 2026年プレプリント](https://arxiv.org/abs/2608.26175) は、英語で学習した抽出圧縮器の結果が、言語と圧縮率によって変わると報告する。日本語は対象10言語に含まれない。したがって日本語で失敗すると断定する材料でも、英語の削減率を日本語へそのまま移す材料でもない。日本語の実測が必要である。

[Prompt Compression in the Wild, 2026年プレプリント](https://arxiv.org/abs/2604.02985) の本文§4.2、§5では、圧縮処理の時間を含めると短い入力や最適化された配信環境で速度改善が限定される。抄録の最大値だけでなく、入力長・実行環境・出力長の条件を確認する必要がある。Opus 4.6の費用や速度を直接検証した結果ではない。

[CDCT, プレプリント](https://arxiv.org/abs/2512.17920) の意味精度と制約遵守を分ける着眼点は参考になる。ただし確認したv1本文には実験総数の72/81などの不整合があり、扱う制約・内容も限定的である。「中間の長さが普遍的に悪い」「極端に短ければよい」という結論は採用しない。

## 現行設計を維持する場合の検証案

以下は文献の結果そのものではなく、このアプリへの提案である。最初は既存の一回生成を維持し、別モデルによる分類・復元・圧縮の追加段階は導入しない。

1. 比較対象を原文、現行圧縮、原語順と原文表現を優先する抽出寄りの一回生成候補に限定する。重要な否定・例外・採用状態・引用の関係は文単位で残し、単純な単語削除を実装しない。
2. 固定の極端な削減率を合格条件にしない。検証では実際の保持率を複数の帯域で記録し、どこから要求や文体が失われるかを見る。短い高密度文では原文を選ぶことも成功とする。
3. 圧縮候補を作る際には見せない複数の後続質問を、同じ保存済み圧縮文に与える。直後の関連質問、別の論点、以前の禁止・例外が有効な質問、物語の続きを含める。
4. 意味・指示・文体を別の判定欄にする。数値、否定、回答創作、話者、訂正範囲を確認する。文体は敬体/常体、人物の声、留保、皮肉、段落や見出し、文字数等を判定する。説明されていない感情は付加しない。
5. 原文による応答も反復する。原文でも生じる違反と圧縮で増えた違反を区別する。機械判定できる形式や文字数は自動確認し、声や含意は原文と並べて人が確認する。[M-IFEvalの日本語評価](https://github.com/lightblue-tech/M-IFEval) は形式・指示遵守の参考にできるが、文体全体の代替評価にはしない。
6. 初期確認は各条件3回、候補の絞り込み後は失敗・未使用ケースを各5回とする。これは小規模検証の提案であり、低頻度の失敗がない証明にはならない。Opus 4.6とFreeモデルの結果は分け、温度・思考設定・利用可能パラメータ・プロバイダを記録する。
7. 削減率は送信に使うモデルの同じ数え方で、実際の置換文と必要な付加文を含めて測る。APIのusageも別記する。生成費用、後続応答の出力費用、再利用回数、キャッシュ条件を含めて費用効果を見る。

削減した後続入力費用の累計が圧縮生成の費用を超えるかどうかを確認する。毎回の出力が長くなる場合やキャッシュ条件が変わる場合には、それも費用差へ含める。トークン削減率だけで費用削減を断定しない。

## 今回の扱い

調査時点では追加の課金検証を停止した。先に試した強圧縮候補と途中結果は `docs/development/evaluations/bubble-summary-extreme-2026-10-06/` に保存済み。途中結果を改善の証拠として採用しない。本番プロンプトはこの調査では変更していない。

次の変更候補は、原文表現を優先して反復を除く一回生成方式とする。LLMLingua-2自体の比較は別の圧縮モデルの実行環境を必要とするため、現行設計の局所調整と分けて判断する。日本語・文体・将来の異なる質問に関する結果を得てから、圧縮率を強める。

調査後、上記の知見をもとに5候補を実モデルで比較した。後続動作の違反が残ったため、全候補不採用とした。[条件・費用・反例・証跡](../evaluations/bubble-summary-downstream-2026-10-06/README.md)を参照。本番プロンプトは維持している。
